# 기술 구조

2026-10-13 로컬 소스 기준. 게임별 런타임·규칙·점수 인코딩은 [게임 문서 색인](games.md)과 각 `GAME_DESIGN.md`를 따른다. 운영 배포 확인과 구분한다.

## 구성

```text
Flutter 앱
├── 일반 UI: Flutter
├── 미니게임 런타임: Flame
├── 게임 공통 인터페이스
└── Supabase 클라이언트
        ↓
Supabase
├── Auth: 익명 사용자, 카카오 identity 및 계정 연결
├── PostgreSQL: 사용자, 게임 일정, 시도, 점수, 집계
├── Edge Functions / RPC: 플레이 권한과 점수 제출 검증
├── RLS: 사용자 데이터 접근 제어
└── Storage: 향후 게임 애셋 및 임시 리플레이
```

## 환경 분리

- 로컬: Mac의 Docker에서 Supabase 실행
- 개발 앱: 로컬 또는 개발용 Supabase 프로젝트 연결
- 운영 앱: 별도의 Supabase Cloud 프로젝트 연결
- DB 변경은 SQL migration으로 관리해 환경 간 동일하게 적용

## 핵심 데이터 개념

- `profiles`: 공개 랭킹 닉네임과 내부 계정 상태
- `games`: 미니게임 메타데이터와 버전
- `daily_games`: 날짜별 공개 게임
- `daily_play_sessions`: 연습/도전 선택, 실제 시작 시각, 대상 게임 날짜
- `attempts`: 공식 기록 제출용 시도와 규칙 스냅샷·사용 상태
- `scores`: 검증된 시도 결과
- `game_rule_versions`: 날짜별 일정과 발급 시도가 참조하는 불변 규칙 버전
- `coin_transactions`: 코인·경험치 거래의 중복 처리 방지 원장
- `leaderboard_aggregates`: 향후 주간·월간 집계 설계 대상으로, 현재 일일 순위와 구분

## 보안 원칙

- 앱이 공식 점수를 테이블에 직접 기록하지 않는다.
- 서버가 발급한 단회성 시도 토큰이 있어야 플레이 결과를 제출할 수 있다.
- 서버 시간을 기준으로 날짜와 제출 가능 여부를 판단한다.
- 점수 규칙과 게임 버전을 함께 저장한다.
- 서버에서 내 순위를 계산하고 내 주변 목록 및 전체 일일 랭킹을 반환한다. 앱이 순위를 재계산하지 않는다.
- Realtime 랭킹은 초기 버전에서 사용하지 않는다.

## 한 판 생명주기

1. 게임 화면 진입 전에 서버가 `issued` 시도를 만든다.
2. 실제 시작을 확인한 뒤 정상 종료 시 게임별 점수·종료 타입·플레이 시간을 제출하고, 서버가 발급된 규칙 스냅샷과 결과 계약을 검증한다. 별 개수나 반응시간 같은 필드는 게임별 계약을 따른다. 연습 결과는 공식 랭킹에 제출하지 않는다.
3. 전화 수신, 홈 전환, 화면 잠금, 앱 백그라운드 전환 시 시도를 `expired`로 만든다.
4. 프로세스 강제 종료로 3번 요청이 실행되지 않아도 다음 앱 실행에서 남은 `issued` 시도를 `expired`로 복구한다.
5. 오늘의 도전이 `submitted` 또는 `expired`일 때만 보상형 광고용 추가 시도 1회를 발급한다.
6. 광고 추가 시도가 소진된 후에는 같은 도전 버튼으로 서버가 보유 도전권을 매번 원자적으로 1장 차감하고 다음 시도를 발급한다. 보유 도전권이 남아 있는 동안 일일 사용 횟수 제한은 없다.

## 일일 게임 일정

- 날짜 경계는 한국 출시 기준 `Asia/Seoul` 오전 6시다.
- 오전 6시 전에 발급된 시도는 해당 시도의 `play_date`로 오전 6시 10분까지 제출할 수 있다.
- 홈 화면은 오전 6시 도달, 앱 복귀, 플레이 시작 직전에 서버 날짜를 확인하고 날짜가 바뀌면 새 게임을 다시 불러온다.
- 전날 결과는 오전 6시 10분에 확정하며, 점수를 제출한 일반 계정의 첫 홈 진입에 한 번만 보여준다.
- 테스트 모드는 설정의 앱 버전을 7회 누른 뒤 서버 PIN 검증을 통과해야 활성화된다. 활성화된 같은 계정은 앱 버전을 다시 7회 눌러 PIN 없이 일반 모드로 돌아갈 수 있다.
- PIN 해시는 클라이언트가 읽을 수 없는 런타임 설정에 저장하고, 5회 실패한 계정은 15분간 인증을 잠근다.
- 당일 일정이 없으면 활성 게임 목록을 날짜 순서로 순환해 서버가 최초 요청 시 생성한다.
- 생성된 일정에는 게임 ID와 규칙 버전을 고정해 둔다. 규칙 메타데이터는 `game_rule_versions`에 불변으로 보관하고, 변경할 때는 같은 게임의 새 버전을 발급한다.
- 새 게임은 앱 클라이언트와 서버 점수 검증이 배포된 뒤에만 활성화한다.

### 점수 전송 장애 복구

- 게임 완료 결과는 서버 전송 전에 기기에 임시 보관한다.
- 전송이 실패하면 다음 홈 진입에서 자동 재전송하고, 결과 화면에서도 즉시 재시도할 수 있다.
- 서버는 이미 `submitted` 상태인 같은 시도에 대해 기존 일일 결과를 다시 반환한다. 응답 유실 뒤 재전송해도 점수가 중복 기록되지 않는다.

## 닉네임과 일일 랭킹

- 닉네임은 `profiles`에 저장하고 소문자 기준 고유 인덱스로 중복을 막는다.
- 자동 발급 닉네임의 첫 설정은 무료이며, 기존 닉네임 변경은 서버가 원자적으로
  `store_nickname_change_tickets` 1장을 차감한 경우에만 허용한다. 변경권은
  코인 상점에서 500코인으로 구매한다.
- 랭킹은 사용자별 당일 최고 점수 하나만 사용하고 원시 점수 내림차순, 제출 시각 오름차순, 사용자 ID 오름차순으로 정렬한다. 빠를수록 좋은 게임도 규칙 모듈에서 높은 값이 좋은 제출 점수로 인코딩한다.
- 실제 사용자 기록만 공식 순위와 참여자 수에 포함한다. NPC 기록은 제외하며 테스트 계정은 다른 사용자의 랭킹에 포함하지 않는다.
- 응답에는 내 주변 3명과 전체 일일 랭킹을 반환한다.
- `get_previous_game_winner`는 해당 게임의 직전 일정부터 찾고 그 회차의 실제 1등을 반환한다. 해당 회차에 점수가 없으면 더 오래된 회차로 대신하지 않는다.
- `get_daily_nonplayers`는 실제 시작 세션 또는 점수가 없는 유저를 제한된 페이지로 반환한다. 대상 게임 날짜에는 내일 게임 연습의 `target_game_date`도 반영한다. 신원미상·본인·테스트·차단 유저를 제외하고 XP 내림차순, 사용자 ID 오름차순으로 조회한다.

## 소셜 액션과 푸시 한도

- 찌르기와 자랑하기는 각각 한국 시간 기준 하루 최대 3회다.
- 앱은 버튼 상태와 성공·한도 초과 안내를 담당하지만, 실제 한도 검증은
  `send_social_action` RPC가 담당한다. 앱 삭제·재설치, 다중 기기, 직접 API
  호출로 우회할 수 없도록 서버 검증을 최종 권위로 둔다.
- 찌르기에는 상대별 6시간 쿨다운을 두지 않는다. 제품 정책은 일일 3회이며,
  같은 상대에게도 남은 횟수 안에서는 보낼 수 있다.
- 소셜 알림은 `social_notifications`에 먼저 저장한 뒤
  `push_notification_outbox`에서 FCM worker가 전송한다. 푸시 전송 실패와
  관계없이 앱의 미확인 소셜 inbox가 fallback으로 남아야 한다.
- 내 기록은 최근 날짜별 최고 점수와 실제 사용자 기준 당시 순위를 반환한다. 앱은 `history_limit=100`으로 조회한다.

## 카카오 계정 연결

- 앱은 익명 Supabase 세션으로 즉시 시작하고, 설정의 `카카오 계정 연결`에서
  Kakao Flutter SDK의 네이티브 로그인 결과를 Supabase Kakao OIDC identity로
  연결한다.
- 설정의 `프로필`에서 닉네임, 코인·경험치·레벨, 카카오 계정 연결을 한곳에서
  관리한다. 홈에는 현재 경제 상태를 요약해서 표시한다.
- 연결 요청에는 Kakao `idToken`, `accessToken`, nonce를 함께 전달한다.
- 새 기기에서 이미 연결된 Kakao identity를 발견하면 해당 Supabase 계정으로
  로그인해 기존 기록을 이어간다. 이 경우 새 기기의 익명 기록은 기존 계정과
  자동 병합하지 않는다.
- 기존 익명 세션의 데이터는 link 성공 시 같은 user ID에 남는다.
- Kakao identity 연결은 기기 변경 시 기록 복원을 위한 선택 기능이며,
  미연결 상태에서도 날짜와 플레이 횟수에 관계없이 게임을 시작할 수 있다.
- 보상형 광고 추가 플레이는 익명 계정에도 허용한다. `prepare_rewarded_ad`와
  `claim_rewarded_attempt` RPC는 Kakao 연결 여부와 무관하게 AdMob 서버 검증,
  일일 횟수, 시도 상태를 서버에서 검증한다.

## 레벨과 보상

- `experience_threshold(L)`은 `(L−1) × (75 × (L−1) + 25)`로 누적 XP 경계를 계산한다. Dart의 `PlayerEconomy`와 서버 `experience_level`·경제 JSON은 같은 150XP 증가 규칙을 사용한다.
- `profiles`의 XP 갱신 트리거가 `level_rewarded_through`보다 새로 높은 레벨 수만큼 `store_challenge_tickets`를 증가시킨다. 코인 원장 응답을 재처리하거나 XP가 감소 후 복구돼도 재지급하지 않는다. 티켓 상한 초과는 해당 거래 전체를 실패시킨다.
- `level_celebration_seen_through`는 축하 화면의 확인 완료 지점이다. `get_pending_level_up_reward` 조회는 무변경이며 `acknowledge_level_up_reward`는 인증 사용자와 화면에 표시한 레벨만 확인한다. 확인 RPC가 보상을 지급하지 않는다.
- 기존 계정은 이전 200XP 증가 규칙의 레벨을 먼저 기록한 뒤 새 규칙으로 재계산해 레벨 차이만 지급한다.
- XP 변경 시 자동 닉네임 색상도 갱신된다. 구형 색상권 RPC 서명과 이력은 호환성 때문에 유지하되 신규 구매·선택·선물은 거절한다.

## 미니게임 확장 원칙

각 게임은 공통 인터페이스를 구현한다.

- 게임 식별자와 규칙 버전
- 시작 및 종료
- 제한 시간
- 점수 산정 결과
- 결과 검증에 필요한 최소 이벤트
- 공통 일시정지·음향·진동 설정

Flutter 화면과 인증·랭킹 로직은 미니게임 구현에서 분리한다.
